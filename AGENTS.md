# Dinvolt internal development

These instructions apply to work on Dinvolt itself. They are not starter content and must not be copied into generated projects or included in the published CLI package, catalog, or installed skills.

## Official documentation

- The open-source documentation site lives in `apps/docs/`, built with Blume for `https://docs.dinvolt.com`. Read `apps/docs/README.md` for development, content ownership and Vercel deployment settings.
- Keep public documentation in English. Reuse the reviewed repository sources selected in `apps/docs/lib/repository-source.ts`; update those sources instead of duplicating their guides. Keep the publication list explicit and exclude internal notes, test reports and credentials.
- The private sibling `dinvolt-landing` repository owns `https://dinvolt.com`, its presentation and branding. Official product guides belong here. Update the landing's command/prompt illustrations when relevant, without importing that repository into the docs build.
- Run `bun run docs:dev` locally; `bun run docs:check` checks types, links and the static build and is included in `bun run check`. Keep the docs application and its dependencies out of the published CLI package.

## Real Turso database for end-to-end tests

- When a development task needs end-to-end verification with real database reads or writes, use the disposable internal Turso database configured in the root `.env.demo.local`. Unit tests and checks that do not need a remote database should remain independent of these credentials.
- The user provided this database for internal testing. Creating, reading, updating, and deleting test records, and applying migrations needed for the test, are authorized. Do not ask for the same authorization again.
- Exercise a Turso demo generated by the local `create` command, preferably under `demos/`. Read that demo's own `AGENTS.md` and database/authentication docs before testing. These Turso credentials do not apply to PlanetScale demos.
- Read only `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` from the root `.env.demo.local` without printing their values. Supply them to the demo's server and migration processes, or merge only those two keys into its ignored `.env.local`. Preserve other demo variables; generate a separate `BETTER_AUTH_SECRET` and set the demo's local `BETTER_AUTH_URL` when testing auth. Do not execute the environment file as shell code.
- Verify the effective database configuration matches the internal test file before any remote mutation, accounting for inherited environment variables and the demo's existing `.env*` files. Do not fall back to other database credentials. If the file or either key is missing, report the missing setup without exposing secrets or claiming that remote verification passed.
- Demos share this database, including tables and migration history. Run schema changes sequentially, inspect the current schema/migration state before applying migrations from a fresh demo, and use uniquely identifiable test data. Clean up records created by the test when practical. Do not reset the entire database or delete unrelated demos' data as routine cleanup.
- Verify the actual application flow and persisted results through the generated app and its database integration. A successful connection, mocked test, typecheck, or build alone does not establish end-to-end success. Report what was exercised, whether real reads/writes passed, and any remaining test data or schema changes.
- Keep credentials out of logs, screenshots, commits, fixtures, `.env.example`, catalog templates, and distribution artifacts. Keep this workflow internal; do not add automatic credential loading to the public `create` command.
- The root `package.json` uses a `files` allowlist for publication. Preserve that boundary and check the package contents when changing distribution settings; root `AGENTS.md`, `.env.demo.local`, and `demos/` must remain excluded.

## Static UI and loading

- In our catalog pages and playground previews, prerender static UI immediately. Keep logos, navigation, headings, descriptions, form fields, filters, table headers and known pagination controls outside session/data waits and their fallbacks.
- Scope Suspense and skeletons to the smallest unresolved dynamic fragments, such as account identity, table rows and unknown totals. Initial loading does not justify replacing an entire page or layout. Preserve existing data during background updates and keep authorization at every sensitive server boundary.
- Verify delayed initial loads as well as background refreshes: static controls must remain mounted and usable, private data must wait for authorization, and the change must not add duplicate session/data requests. Keep the generated instructions in `catalog/ui/agent-instructions.md` and `catalog/trpc/agent-instructions.md` consistent with this policy.

## Internal linting and formatting

- Use Ultracite 8 with Oxlint + Oxfmt. Run `bun run fix` to apply safe fixes and formatting, or append a file path to limit the operation. Run `bun run lint` to check lint and formatting without modifying files.
- Run `bun run check` before completing code changes; it includes lint, TypeScript, the CLI/registry build and the test suite. `bun run format:check` checks formatting alone.
- Universal editor settings live in `.vscode/settings.json`; install the recommended `oxc.oxc-vscode` extension for format and fixes on save.
- The root configuration checks our CLI, scripts, tests, tooling and own catalog and playground files. React rules apply to TSX; Next.js rules apply to catalog and playground TSX. These templates are not a standalone root Next.js app.
- `tooling/ignores.ts` shares exclusions between lint and format. Preserve vendored shadcn components/examples and their upstream hashes; demos and installed skills retain their own configurations. Keep our icons and registry blocks included. Do not exclude the entire catalog to hide diagnostics.
- Function declarations and arrow functions are both accepted. Keep meaningful object key order and sequential scaffolding/cleanup operations. Async test doubles may implement Promise-returning contracts without awaiting; fixture non-null assertions are permitted in tests. Other exceptions need a concrete reason in the configuration or next to the affected code.
- Keep these settings and instructions internal. Preserve the publication `files` allowlist and the existing runtime dependency on Ultracite used by `create`; do not copy root tooling into generated projects.
